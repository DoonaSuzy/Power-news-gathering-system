## 八、亮点提炼（面试可主动展开的技术细节）

1. **瑞数动态防护（RiverSecurity）突破**：国网省级站返回 **412 + 混淆 JS 挑战**，
   常规请求头伪造无效。最终方案是 **CDP 直驱真实 Chrome**（WebSocket，
   `Page.navigate` 轮询 DOM 稳定），并用 `--user-agent` 覆盖掉
   `HeadlessChrome` 指纹 + `--disable-blink-features=AutomationControlled`
   消除 `navigator.webdriver`，才拿到挑战 Cookie。**关键坑是 UA 里残留
   `HeadlessChrome` 会导致挑战返回 39 字节空白页**。

2. **三层去重体系**：URL 指纹（库内唯一键强一致）→ Redis 日期分桶布隆位图
   （跨任务快速判重，2MB/桶）→ 正文 SimHash 64 位 + 汉明距离
   （识别跨省转载通稿，电力新闻转载率极高）。

3. **Worker 子进程隔离**：Twisted 反应器**无法在同一进程内重启**，
   因此每次任务拉起独立子进程 `python -m newsagg run-job <id>`，
   父进程 **XACK 前必须等子进程写成功**。副作用是单站点内存爆炸不会拖垮整个池。

4. **多实例幂等建批**：`crawl_jobs` 表用 `(source_id, trigger_key)` 唯一键，
   多个调度实例并发跑也只会建出一份任务，无需分布式锁。

5. **MySQL 8.4 保留字踩坑**：`YEAR_MONTH` 在 MySQL 8.4 升级为保留字
   （INTERVAL 间隔单位），列名照写直接报 1064，最终改名 `published_ym`。
   排查手法是逐列增量建表二分定位。

比"我写了 31 个接口"更能体现工程能力。

### 1. `pool_pre_ping` 触发 aiomysql 签名不匹配（最隐蔽）

- **现象**：服务启动时依赖探活三项全 `ok`，但**任何请求**打到需要数据库的接口就 500。
- **根因链**：SQLAlchemy 的 aiomysql 方言没有自己的 `do_ping`，沿用了 pymysql 的版本；
  而那一版是靠 **import 本机的 PyMySQL** 看 `ping` 的默认值来决定调用形态。
  venv 里 PyMySQL 的签名是 `ping(self, reconnect=False)` → 判定"不传参"→ 调
  `dbapi_connection.ping()`；可 aiomysql 适配器的签名是 `ping(reconnect)`（**必传**）
  → `TypeError`。
- **为什么迷惑**：首次连接新建连接、不做 pre-ping，所以**第一次查询是成功的**；
  只有连接**归还池后第二次借出**才炸。表现为"启动全绿、一用就挂"。
- **验证手法**：写最小复现脚本，`pool_size=1` 连续两次 `connect()`，
  卡出来的调用栈直接指向 `pymysql.py: do_ping`。
- **修复**：为 aiomysql 方言显式覆盖 `do_ping`，调用 `ping(False)`（只探测不重连），
  让行为不再取决于第三方包的版本组合。升级/降级 SQLAlchemy 都无效（2.0.36 / 2.0.43 均复现）。
- **收获**：`pool_pre_ping` 属于"只有真实连接池才会走到的代码路径"，**mock 永远测不出来**。

### 2. `COUNT(*)` 套 `COUNT(*)` 导致分页总数恒为 1

- **现象**：`GET /articles` 返回 `total=1`，但 `GET /articles/count` 返回 `total=826`。
  同一个表、同一套筛选条件，两个接口给出互相矛盾的数字。
- **根因**：分页工具会在传进来的查询外面再套一层 `COUNT(*)`：
  `SELECT count(*) FROM (<count_from>)`。而调用方传进来的 `<count_from>`
  **本身已经是** `SELECT count(*) ...`（恒返回 1 行）→ 外层统计到的是"1 行"。
- **修复**：把 `count_from` 语义明确为"**产出行**的子查询"（只取主键），
  并把这个约束写进方法名 `_paginate_count_source` 与 docstring。

### 3. 导出循环不推进游标 → 100 份重复数据

- **现象**：导出 CSV 得到 **50000 行 / 270MB**，而全库只有 826 篇。
- **根因**：取数方法只写了 `LIMIT` 而**没有 `OFFSET`**，调用方却是
  "取到不足一批才停"的循环 → 每一轮都拿回**同一批 500 行**，
  直到撞上 50000 行的上限。
- **修复**：把 `offset` 显式提到方法签名上，循环按已取行数推进。
  导出体积 **270MB → 4.0MB**，行数 50000 → 826。
- **收获**：把 `offset` 藏在 `ArticleQuery.page` 里，会让人误以为"不传也行"；
  放在签名上，漏传就是一个显式的 `TypeError` 而不会是静默错数据。

### 4. 用「只读会话」写数据 → 接口返回 200，数据却没了

- **现象**：`POST /sources` 返回 `200` 且**带着自增 id=46**，
  但回查数据库仍是 45 行，什么都没多。
- **根因**：采集库会话按"只读"设计（退出时不 `commit`），
  而写入方法只 `flush` 不 `commit` → 会话关闭时被**静默回滚**。
  API 层看起来完全成功（连自增 id 都拿到了），只有回查数据库才会发现。
- **修复**：三件事一起做——① 引入显式的"采集库写会话"依赖，
  让"这个路由会改采集库"在函数签名里可见；
  ② 事务提交上移到服务层，保证提交发生在 `audit_write` 的作用域内
  （否则审计日志会在提交前就写成"成功"，一旦提交失败，日志与事实相反）；
  ③ 在只读会话的 docstring 里写明"拿它做写操作会被静默回滚"。

### 5. 接口数值边界与 DDL 列类型不一致 → 裸 500

- **现象**：`POST /sources` 传 `crawl_interval_hours=168` 返回 500。
- **根因**：接口校验写的是 `le=168`，但 `sql/schema.sql` 里这列是
  **`TINYINT`（有符号，上限 127）**。Pydantic 放行 → MySQL 报
  `1264 Out of range value` → 走到兜底异常处理器变成 500。
- **修复**：① 接口上限对齐 DDL 改为 127；
  ② **新增 `DataError` / `IntegrityError` 全局处理器**，把"入参越界"这类
  客户端问题映射成 422（业务码 1002）/ 409，不再让它们伪装成服务端故障——
  否则前端会重试、告警会误报。
- **收获**：这是一整类问题（**校验边界 vs 存储容量**）的代表。
  教训是改 `Field` 边界时必须同时看 DDL，反之亦然。

> **共性**：这 5 个问题里，有 4 个的症状都"看起来像成功"
> （200 + 自增 id、total=1、50000 行、启动探活全 ok），
> 全靠**对真实库做端到端断言**才暴露。
> 因此本轮产出的 `scripts/e2e_smoke.py`（47 项）与
> `tests/test_platform_regressions.py`（13 项）都保留在仓库里，
> 作为这几类缺陷的长期防线。

## 十一、四条效果是怎么量出来的（算法 + 命令 + 边界）

四份测量脚本随仓库提交，数字不靠回忆。共同前提：

```bash
export POWERSDK_API_BASE_URL=http://192.168.101.84:8080/api/v1
export POWERSDK_API_TOKEN=...      # 只走环境变量，不落任何文件
```

### 11.1 「3 行代码 / 提升 80%」：分母钉成"要写多少行生产代码"

「效率提升 80%」没有分母就是空话，所以把口径钉死：**完成同一个需求，业务侧要写多少行代码**。
需求 = 取广东 2024-01-10~01-12 的逐时气温，得到 `[ts, region, value, unit]` 标准化长表 + 准确率。

* **SDK 侧**：`import` 一行、`PowerDataClient()` 一行、`query(...)` 一行 = **3 行**；
* **基线侧**：`scripts/no_sdk_baseline.py` 里的 `baseline_query`——不用 SDK，自己翻页、
  拆统一响应信封、判业务错误码、按 `decimal→str` 转数值、组装 DataFrame、解析时间戳、
  去重排序、贴单位列、算空值/越界准确率。行数用 `inspect` + AST 现算，
  剔掉空行、整行注释与 docstring。

两条防注水的硬约束：**基线必须与 SDK 产出同一张表**（脚本断言列、行数、逐格差异，
不一致就返回码 1）；**只数函数体**，不数 import 和打印。

```bash
python scripts/no_sdk_baseline.py --start 2024-01-10 --end 2024-01-12
```

实测输出：

```
基线（不用 SDK，直连中台）：72 行 / 1 地区，准确率 1.000000
SDK（5 行函数体，业务侧写法 3 行）：72 行，准确率 1.000000
两张表一致：列=True 行数=True 差异=0 处
同一件事的代码量：44 行 → 3 行，降幅 93.2%
```

> 基线里最容易被忽略、也最能说明"SDK 到底替业务挡了什么"的一处：中台把 `decimal`
> 序列化成**字符串**（为保住小数位），手写侧不加 `to_numeric` 就会在比较运算上
> 直接 `TypeError: '<' not supported between instances of 'str' and 'float'`。

### 11.2 「准确率 99.8%」：158 万行真数据 + 注入缺陷的召回率

「准确率」= `ValidationReport.accuracy` = **去重后的合格行 / 总行**，
一条规则口径：空值 / 越界 / 重复键 / 时间倒退算 error（扣分），单位不符 / 时间轴缺口算 warning（不扣分）。

只报"符合声明区间"是不够的——**区间写错，准确率就只是画像与现实的差距**。所以两件事一起做：

1. **真库全量审计**：`scripts/accuracy_audit.py --emit-sql` 生成对 24 张 `wx_*` 表 ×
   10 个要素列的 UNION ALL 计数 SQL（**区间直接从 `powersdk` 导入，不复制常量**），
   在 VM 上跑完把 TSV 拉回本地 `--from-tsv` 汇总。

   ```bash
   python scripts/accuracy_audit.py --emit-sql > .workbuddy/tmp/sql/04_audit.sql
   tr -d '\r' < .workbuddy/tmp/sql/04_audit.sql > .workbuddy/tmp/sql/04_audit_lf.sql
   scp .workbuddy/tmp/sql/04_audit_lf.sql zhu@192.168.101.84:/home/zhu/sql/
   ssh zhu@192.168.101.84 '/home/zhu/rx.sh power_news /home/zhu/sql/04_audit_lf.sql'
   scp zhu@192.168.101.84:/home/zhu/sql/04_audit_lf.tsv .workbuddy/tmp/04_audit.tsv
   python scripts/accuracy_audit.py --from-tsv .workbuddy/tmp/04_audit.tsv
   ```

   结果：**1,583,025 行，空值 0、越界 0，准确率 100.000000%（阈值 0.998 达标）**。
   对照：改造前那版画像（风速按 `m/s`、上界 40；`weather_code` 借了气温的 60 上界）
   扫同一批数据会判出 **508 + 37,960 = 38,468 行假越界 → 97.57%**，
   并且直接把 `accuracy_below_threshold` 告警打出来。**这就是"区间必须来自库"的代价差**。

2. **召回率**：`scripts/validation_recall.py` 往一条已知序列上注入**数量已知**的坏点
   （空值 3、越界低 2、越界高 2、重复键 2、时间倒退 1、单位不符 2 = 12 个），
   先验证干净数据 0 误报，再验证 12 个全被抓到。

   ```bash
   python scripts/validation_recall.py --category weather --param wind_speed_10m \
       --region 广东 --start 2024-01-01 --end 2024-01-12 --rows 240
   ```

   中台实连结果：240 行干净数据准确率 **1.0**、误报 **0**；注入后各违规计数
   `{null_value:3, out_of_range:4, duplicate_key:2, non_monotonic:1, unit_mismatch:2}`
   **与注入数量逐条相等**，召回率 **100%**，脏数据准确率 **0.958678 < 0.998**（跌破阈值）。
   离线内存源（200 行）同样 100% 召回 / 0 误报，脏数据 0.9505。

> 两个坑（写进代码注释了）：注入位置必须互不重叠——把第 10 行的时间戳倒拨 1 小时，
> 会和第 8 行注入的重复时间戳**撞车**，导致 `duplicate_key` 少数一个、召回率算出 110%；
> 重复键只能从**末行**复制。`region` 必须传**省份**（`广东`），传大区名（`华北`）会
> 抛 `UnknownRegionError`——大区×产品的扇出是 SDK 内部行为，不是调用方参数。

### 11.3 「10 万条 12 秒 → 1.5 秒」：比值可复现，绝对值不可

`scripts/bench_vectorized.py` 在**同一批输入**上跑三条路径，并且**先断言结果一致再谈耗时**：

| 路径 | 中位耗时 | 每行 | 相对向量化 |
| --- | --- | --- | --- |
| 向量化管线 `vectorized_transform` | **0.1213s** | 1.21 µs | 1× |
| 逐行参照（典型写法 `iterrows`） | 1.3483s | 13.5 µs | **11.12×** |
| 逐行参照（认真优化过，`itertuples`） | 0.2563s | 2.6 µs | **2.11×** |

一致性：两条逐行路径与向量化输出 **100,062 行逐格对齐**，最大相对误差 2.2e-16，
无 NaN 差异。JSON 落在 `.workbuddy/tmp/bench_100k.json`。

> **为什么报两个基线**：只报 `iterrows` 那 11 倍，会把"别用逐行循环"的收益全记在
> 向量化头上。对"一个认真写、用 `itertuples` 的逐行实现"，真实收益是 **2.11 倍**。
>
> **诚实边界**：简历里"从 12 秒降至 1.5 秒"的绝对值在本机复现不出来——本机逐行参照
> 是 1.35 秒（和"1.5 秒"同一量级），向量化 0.12 秒。**可复现的是量级与比值**：
> 8 倍（简历口径）与实测 11 倍（对典型写法）/ 2.1 倍（对优化过的逐行）。
> 参照实现必须与 `fill_gaps` 走**同一张全局时间网格**（网格取自整批 min/max，不是每个
> 地区自己的首个已知点），否则行数会差 2 行，被误读成"向量化有 bug"。
>
> `VectorizedResult.row_loops` 恒为 0 这件事也顺手改口了：它声明的是**这条路径的实现契约**
> （有没有逐行 Python 循环），**不是性能指标**，测试可以断言它，答辩不能拿它当证据。

### 11.4 「复用率 60% / 新接口 2 小时」：13 行声明 vs 实际执行到的 254 行

做法：把 LNG 行情（库里已有 `lng_spot`，140 行 / 25 个地区 / 11 个口径）接成 SDK 的第 12 类。

（按文件去重），而不是"模块一共有多少行"——没跑到的代码不算复用。帧回调对包外文件返回
`None`，避免把 pandas 内部每一行都跟一遍。

```bash
python scripts/new_category_reuse.py --start 2026-09-01 --end 2026-10-12 --json out.json
```

实测（中台真实数据，`lng_price` / 全地区 / 默认 CLP 口径）：

```
  validation.py 62 / http_source.py 59 / parsing.py 54 / client.py 31
```

## 十二、这一轮为对标做的事，本质是"把不能复现的措辞换成能复现的"

5 个真实缺陷，全部由"拿真库/真接口量一遍"暴露，不是读代码读出来的：

1. **校验区间用了合成画像，而不是库口径**。`WEATHER_PARAMS` 是离线演示发生器用的形状参数，
   风速历史上写的是 `m/s`、上界 40；库里 Open-Meteo 的风速是 **km/h**，实测到过 72.1。
   拿画像卡真库 → **38,468 行假越界、假准确率 97.57%**、告警刷屏。
   修复：新增 `WEATHER_COLUMN_RANGE` / `DAILY_RANGE_OVERRIDES` / `weather_range()`，
   与 `WEATHER_COLUMN_UNIT` **成对维护**；`spec_for_category` 气象分支改走库口径，
   未知要素抛 `UnavailableParamError`，**不再悄悄借气温的区间顶上去**；
   `WEATHER_PARAMS` 的风速画像同时改成 km/h，让离线源不再被自己的校验判成"单位不符"。

2. **`non_monotonic` 是一条永不触发的死规则**：实现先 `sort_values(["region","ts"])`
   再 `diff()`，排完序当然不会倒退，所以"时间倒退"这条检查**从来没工作过**。
   修复：按**到达顺序**判定（同地区内后一行不得早于前一行），并加显式回归用例
   （把末行时间戳倒拨一小时必须被抓到；同一份数据排好序再校验则必须干净）。

3. **`validate()` 遇到文本日期列直接崩**：`price_date` 这类列从库里/接口里可能是 `str`，
   对字符串列 `diff()` 抛 `TypeError`，取 `min/max` 去 `date_range()` 会把**字典序**当时间轴。
   修复：时间相关的三条规则统一先 `to_datetime`，解析不了的**按空值扣分**。

4. **单位写法不折叠 → 行情类每一行都报"单位不符"**：`market_prices.unit` 存中文
   "元/兆瓦时"，类别画像写"元/MWh"，同量纲不同拼法。修复：`UNIT_ALIASES` + `canonical_unit()`
   只在 warning 比较时折叠写法，**不换算、不改数据**。

5. **`query()` 的校验粒度口径错位**：`expected_freq` 原来固定按 1 小时网格卡，
   `granularity="daily"` 时缺口率被虚报成接近 100%，刷出一屏没有信息量的告警。
   修复：`expected_freq` 跟输出粒度走（`granularity_freq`），而**取值区间仍按逐时口径**——
   库里存的逐日行是日累计（量纲不同），而 `query()` 是取逐时行本地重采样，输出是小时量纲。

另外把 `default_source()` 的判据写成了**只看环境变量**：三套环境画像（dev/test/prod）的
`api_base_url` 都非空，拿 `Settings.api_base_url` 当判据会让每一次 `PowerDataClient()`
都去打一个不存在的端口——离线演示与"开箱即取真数据"两头全毁。
