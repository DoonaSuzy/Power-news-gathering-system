## 八、亮点提炼（面试可主动展开的技术细节）

1. **瑞数动态防护（RiverSecurity）突破**：国网省级站返回 **412 + 混淆 JS 挑战**，
   常规请求头伪造无效。最终方案是 **CDP 直驱真实 Chrome**（WebSocket，
   `Page.navigate` 轮询 DOM 稳定），并用 `--user-agent` 覆盖掉
   `HeadlessChrome` 指纹 + `--disable-blink-features=AutomationControlled`
   消除 `navigator.webdriver`，才拿到挑战 Cookie。**关键坑是 UA 里残留
   `HeadlessChrome` 会导致挑战返回 39 字节空白页**。

2. **三层去重体系**：URL 指纹（库内唯一键强一致）→ Redis 日期分桶布隆位图
   （跨任务快速判重，2MB/桶）→ 正文 SimHash 64 位 + 汉明距离
   （识别跨省转载通稿，电力新闻转载率极高）。

3. **Worker 子进程隔离**：Twisted 反应器**无法在同一进程内重启**，
   因此每次任务拉起独立子进程 `python -m newsagg run-job <id>`，
   父进程 **XACK 前必须等子进程写成功**。副作用是单站点内存爆炸不会拖垮整个池。

4. **多实例幂等建批**：`crawl_jobs` 表用 `(source_id, trigger_key)` 唯一键，
   多个调度实例并发跑也只会建出一份任务，无需分布式锁。

5. **MySQL 8.4 保留字踩坑**：`YEAR_MONTH` 在 MySQL 8.4 升级为保留字
   （INTERVAL 间隔单位），列名照写直接报 1064，最终改名 `published_ym`。
   排查手法是逐列增量建表二分定位。

## 九、管控层上线过程中修掉的 5 个真问题（面试强素材）

这一轮"补齐 FastAPI 后端"不是把骨架接上路由就完事——**端到端跑真库**才暴露出来的
5 个缺陷，每一个都属于"代码看着对、跑起来静默错"的类型。这类问题的排查过程，
比"我写了 31 个接口"更能体现工程能力。

### 1. `pool_pre_ping` 触发 aiomysql 签名不匹配（最隐蔽）

- **现象**：服务启动时依赖探活三项全 `ok`，但**任何请求**打到需要数据库的接口就 500。
- **根因链**：SQLAlchemy 的 aiomysql 方言没有自己的 `do_ping`，沿用了 pymysql 的版本；
  而那一版是靠 **import 本机的 PyMySQL** 看 `ping` 的默认值来决定调用形态。
  venv 里 PyMySQL 的签名是 `ping(self, reconnect=False)` → 判定"不传参"→ 调
  `dbapi_connection.ping()`；可 aiomysql 适配器的签名是 `ping(reconnect)`（**必传**）
  → `TypeError`。
- **为什么迷惑**：首次连接新建连接、不做 pre-ping，所以**第一次查询是成功的**；
  只有连接**归还池后第二次借出**才炸。表现为"启动全绿、一用就挂"。
- **验证手法**：写最小复现脚本，`pool_size=1` 连续两次 `connect()`，
  卡出来的调用栈直接指向 `pymysql.py: do_ping`。
- **修复**：为 aiomysql 方言显式覆盖 `do_ping`，调用 `ping(False)`（只探测不重连），
  让行为不再取决于第三方包的版本组合。升级/降级 SQLAlchemy 都无效（2.0.36 / 2.0.43 均复现）。
- **收获**：`pool_pre_ping` 属于"只有真实连接池才会走到的代码路径"，**mock 永远测不出来**。

### 2. `COUNT(*)` 套 `COUNT(*)` 导致分页总数恒为 1

- **现象**：`GET /articles` 返回 `total=1`，但 `GET /articles/count` 返回 `total=826`。
  同一个表、同一套筛选条件，两个接口给出互相矛盾的数字。
- **根因**：分页工具会在传进来的查询外面再套一层 `COUNT(*)`：
  `SELECT count(*) FROM (<count_from>)`。而调用方传进来的 `<count_from>`
  **本身已经是** `SELECT count(*) ...`（恒返回 1 行）→ 外层统计到的是"1 行"。
- **修复**：把 `count_from` 语义明确为"**产出行**的子查询"（只取主键），
  并把这个约束写进方法名 `_paginate_count_source` 与 docstring。

### 3. 导出循环不推进游标 → 100 份重复数据

- **现象**：导出 CSV 得到 **50000 行 / 270MB**，而全库只有 826 篇。
- **根因**：取数方法只写了 `LIMIT` 而**没有 `OFFSET`**，调用方却是
  "取到不足一批才停"的循环 → 每一轮都拿回**同一批 500 行**，
  直到撞上 50000 行的上限。
- **修复**：把 `offset` 显式提到方法签名上，循环按已取行数推进。
  导出体积 **270MB → 4.0MB**，行数 50000 → 826。
- **收获**：把 `offset` 藏在 `ArticleQuery.page` 里，会让人误以为"不传也行"；
  放在签名上，漏传就是一个显式的 `TypeError` 而不会是静默错数据。

### 4. 用「只读会话」写数据 → 接口返回 200，数据却没了

- **现象**：`POST /sources` 返回 `200` 且**带着自增 id=46**，
  但回查数据库仍是 45 行，什么都没多。
- **根因**：采集库会话按"只读"设计（退出时不 `commit`），
  而写入方法只 `flush` 不 `commit` → 会话关闭时被**静默回滚**。
  API 层看起来完全成功（连自增 id 都拿到了），只有回查数据库才会发现。
- **修复**：三件事一起做——① 引入显式的"采集库写会话"依赖，
  让"这个路由会改采集库"在函数签名里可见；
  ② 事务提交上移到服务层，保证提交发生在 `audit_write` 的作用域内
  （否则审计日志会在提交前就写成"成功"，一旦提交失败，日志与事实相反）；
  ③ 在只读会话的 docstring 里写明"拿它做写操作会被静默回滚"。

### 5. 接口数值边界与 DDL 列类型不一致 → 裸 500

- **现象**：`POST /sources` 传 `crawl_interval_hours=168` 返回 500。
- **根因**：接口校验写的是 `le=168`，但 `sql/schema.sql` 里这列是
  **`TINYINT`（有符号，上限 127）**。Pydantic 放行 → MySQL 报
  `1264 Out of range value` → 走到兜底异常处理器变成 500。
- **修复**：① 接口上限对齐 DDL 改为 127；
  ② **新增 `DataError` / `IntegrityError` 全局处理器**，把"入参越界"这类
  客户端问题映射成 422（业务码 1002）/ 409，不再让它们伪装成服务端故障——
  否则前端会重试、告警会误报。
- **收获**：这是一整类问题（**校验边界 vs 存储容量**）的代表。
  教训是改 `Field` 边界时必须同时看 DDL，反之亦然。

> **共性**：这 5 个问题里，有 4 个的症状都"看起来像成功"
> （200 + 自增 id、total=1、50000 行、启动探活全 ok），
> 全靠**对真实库做端到端断言**才暴露。
> 因此本轮产出的 `scripts/e2e_smoke.py`（47 项）与
> `tests/test_platform_regressions.py`（13 项）都保留在仓库里，
> 作为这几类缺陷的长期防线。
